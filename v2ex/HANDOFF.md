## 1. 背景

用户反馈两件事:

1. 通知显示「签到成功」，网站上实际没有签到。
2. 更早的版本显示「成功」，但**报告的日期和余额都是昨天的**。

第 4 轮拿到了用户的真实运行日志，两个现象被同一条事故链完整解释（见第 2 节）。

## 2. 根因（已由真实日志证实）

用户 2026-10-22 08:15 的运行日志（用户名与余额已脱敏）:

```
签到请求已提交
用户: <用户名>
今日: 20261021 的每日登录奖励 1 铜币     ← 昨天的日期
余额: <余额>
```

旧脚本 `get_daily_url()` 的第一条正则是 `location\.href\s*=\s*'([^']+)'`，
它取页面里**第一个** `location.href` 赋值。在真实 daily 页上，那个值是:

```
/signout?once=89570        ← 登出链接, @偏移 3846
```

真正的 `/balance` 在 @18060，`/mission/daily/redeem` 在**已签到页上根本不存在**。

完整事故链:

| 步骤 | 旧代码行为 | 后果 |
|---|---|---|
| 1 | `get_daily_url()` 命中 `/signout?once=89570` | 把登出链接当成签到入口 |
| 2 | `GET /signout?once=89570`，`requests` 跟随跳转拿到 200 | 打印「签到请求已提交」，**实际没签到** |
| 3 | 再请求 `/balance`，用 `parse_balance()` 抓旧记录 | 「今日」= `20261021 的每日登录奖励 1 铜币` |
| 4 | `success = bool(today or balance or days)` | 余额能解析 → **恒为 True** |

所以通知里的「今日」和「余额」全部来自 `/balance` 页的历史记录，
**与今天签没签到毫无关系**；脚本从没发出过一次真正的签到请求。

> 补充: 用户确认 Cookie 未因登出失效（V2EX 的 `/signout` 可能另有校验），
> 但仍加硬防护，见 4.2。

## 3. 从真实 HAR 确认的事实

HAR 是用户 **2026-10-22 08:54 手动签到成功**的记录，共 29 条请求。
手动签到链路极简: `GET /mission/daily` → 取出 `once` → `GET /mission/daily/redeem?once=43619`
→ 302 回 `/mission/daily`（此时已是已签到状态）。**没有任何表单、XHR、CSRF token。**

| 事实 | 依据 |
|---|---|
| 签到入口 `/mission/daily/redeem?once=43619` | entry[00]，`once` 只有 **5 位数** |
| redeem 返回 **302 且 body 为空**，`location: /mission/daily` | entry[00] `status=302`, `bodylen=0` |
| 领取成功后**跟随跳转的 daily 页**里才有结果 | entry[01] `status=200`, 21KB |
| 成功提示是 `<div class="message">已成功领取每日登录奖励 18 铜币</div>` | entry[01] |
| 已签到标记是 `每日登录奖励已领取` | entry[01]，在 `<span class="gray">` 里 |
| 已签到后**页面不再有 redeem 链接**，只剩「查看我的账户余额」按钮 | entry[01]，全页 `redeem` 0 处 |
| 余额区是 `<a href="/balance" class="balance_area">`，**不是 div、没有 bigger** | entry[01] `id="money"` |
| 余额区里每个数字后面跟 `<img ... height="16" ... @2x.png>` | 同上，所以不能直接对片段 findall 数字 |
| 连续登录文案 `已连续登录 268 天` | entry[01] |
| 页面里还有 **2 个无关的 `once=89570`**（登出、夜间模式） | `/signout?once=`、`/settings/night/toggle?once=` |
| 页面里有当天日期标记 `v2ex:member:<UID>:20261022` | entry[01]，可作「页面是否为今天」的旁证 |
| 浏览器请求头含 `sec-ch-ua`、`Sec-Fetch-*` 全套 | entry[00]/[01] |

## 4. 改动汇总 (`v2ex/main.py`)

### 4.1 核心: 结果判定不再谎报

`success` 只由「到账确认」决定。确认条件是二选一：

1. 领取响应页出现 `已成功领取每日登录奖励` / `每日登录奖励已领取`
2. 回读 `/mission/daily` 页面出现 `CLAIMED_MARKERS`

两者都没有 → `success=False`，并写清卡在哪一步：
「领取未生效（页面仍显示可以领取）」或「无法确认领取状态」。
所有 success 路径统一收敛到 `build_success_result()`，没有第二个地方能把 success 置 True。

### 4.2 真实页面/日志暴露、已修正的问题

| 位置 | 问题 | 现做法 |
|---|---|---|
| **入口提取** | `location.href` 宽松匹配，命中页面第一个 `/signout?once=` —— **本次事故核心** | 正则强制完整路径 `/mission/daily/redeem?once=` |
| **入口硬防护** | 无 | `redeem()` 用 `REDEEM_PATTERN.fullmatch()` 校验，不匹配直接拒绝、不发请求 |
| **成功判定** | `success = bool(today or balance or days)`，与签到无关 | 只由「已成功领取」/「已领取」文准确认 |
| **余额解析** | 按 `<div class="balance_area bigger">` 找，真实是 `<a class="balance_area">` —— **完全解析不到** | 正则同时接受 `</a>` 和 `</div>` 闭合 |
| **余额数字** | 直接对片段 `findall(r"\d+")`，会把 `height="16"`、`@2x.png` 一起抓进来 | 先 `strip_tags` 再取数字，恰好 3 个才认 |
| 余额请求 | 每次都额外拉 `/balance` | daily 页自带余额区，就地解析；解析不到才回退 `/balance` |
| 请求头 | 缺浏览器的 `sec-ch-ua` / `Sec-Fetch-*` | 按 HAR 补齐 |
| 已签到判定 | `SIGNED_KEYWORDS` 含「已领取」等宽松词 | 收紧为整句 `每日登录奖励已领取`，并补英文页 |
| 重新点击 | 不处理「请重新点击一次以领取每日登录奖励」 | 识别后刷新重取 once，最多补一次 |
| redeem 判定 | 不跟随跳转，只看 302 + location | 跟随跳转，最终落到 `/signin` 判登录失效 |
| Cookie 解析 | `SimpleCookie` 会改写含特殊字符的值 | 改为按 `;` 手工拆分 |
| 奖励解析 | `每日登录奖励 N 个铜币`（真实文案没有「个」） | 三条模式覆盖真实文案 |

### 5.2 已签到分支（2026-10-22 实测通过）

同一天重复运行时:


只发 1 个请求（仅 `/mission/daily`），不再重复领取，也不再额外拉 `/balance`。

> 该分支**不会打印 `今日:`** —— 这不是 bug。`已成功领取每日登录奖励 N 铜币`
> 那个横幅只在「刚点完领取那一次」的响应里出现（页面上带 `slideUp` 会自动消失），
> 之后重新访问 daily 页不再渲染它。当天奖励已经在第一次签到时报过了。

### 5.4 仍存的不确定点（不影响使用）

- `CLAIMED_MARKERS` 里的「今日的登录奖励已领取」是推测的备选文案，真实页面只出现过
  「每日登录奖励已领取」。留着无害，只是兜底。
- 签到成功分支的回归用的是「反推的未签到页」，真实未签到页按钮文案未采集过；

### 5.5 本地复现方法

```powershell
$env:v2ex = '{"accounts":[{"account_name":"测试","cookie":"A2=xxx; PB3_SESSION=xxx"}]}'
$env:V2EX_DEBUG = '1'
python v2ex\main.py
```

**重点看这几点**:

1. 日志里应出现 `发现签到入口: /mission/daily/redeem?once=xxxxx`（**不能出现 signout**）
2. 未签到时出现 `第 N 次领取: HTTP 2xx` + `已确认今日奖励到账`
3. `今日:` 必须是当天数字，不能是 `2026xxxx 的每日登录奖励`
4. 同一天重复跑应打印 `页面显示今日奖励已领取，无需重复领取`，且只发 1 个请求

无凭据时可以只跑「假 Cookie」路径验证登录失效分支:
```powershell
$env:v2ex='{"accounts":[{"account_name":"t","cookie":"A2=fake; PB3_SESSION=fake"}]}'
python v2ex\main.py    # 应输出：Cookie 已失效或未登录
```

## 6. 经验记录

- **「报成功」和「真成功」必须是同一条判定链**。`verified` 算得没错，但没接到 `success` 上，
  就是一个看起来严谨、实际永真的检查。
- **`success = bool(A or B or C)` 是危险信号**。三个值只要有一个能从无关页面解析出来，
  成功判定就恒为真。成功必须由「本次动作产生了预期效果」直接决定。
- **对「第一个匹配」保持怀疑**。`re.search` 取首个结果，而页面 DOM 顺序里
  第一个可疑链接往往是导航/登出，不是业务入口。匹配模式必须锚定业务路径。
- **桩数据自造页面会掩盖真问题**。按惯例写的余额正则在自造页面上全绿，
  但真实页面上类名挂在 `<a>` 而非 `<div>`，一个数字都取不到。有 HAR 就用 HAR。
- **提取 token 必须带完整路径**。V2EX 同一页面里有 3 种 `once=`，
  宽松匹配会拿到登出用的 token。
- **告警信噪比要偏向「宁误报失败」**。签到这类用户会去网站核对的场景，谎报成功代价远大于误报失败。
- **用户的一句话往往比代码分析更有信息量**。「显示的是昨天的日期和余额」直接指向
  「数据来自历史记录而非本次签到」，比我从代码里推「读了缓存」准确得多。
- **代码改了就要动版本号**。本轮加了版本号后，又改了 `V2EX_DEBUG` 的解析却忘了升版本，
  导致用户从版本号上看不出区别 —— 版本号的唯一意义就是区分，不动它就等于没有。
- **`commit` 不等于 `push`**。青龙从远程仓库取文件，只 commit 不 push 等于没改，
  本轮因此白测了一轮。改完要确认 `git status -sb` 无 `ahead`。
- **`bool(os.getenv("X"))` 不是开关**。字符串 `"0"`、`"false"`、`"no"` 都是真值。
  开关必须显式比较白名单，并提供一个可观测的「开关状态」输出（本例的 `调试模式:` 行）。

## 7. 后续维护提示

- **签到失败时先开调试**: `V2EX_DEBUG=1`，日志会打印领取结果页摘要（300 字），
  能直接看到 V2EX 返回了什么。用完记得改回 `0` 或删掉。
- **V2EX 改版的高风险点**（按脆弱程度排序）:
  1. `CLAIMED_MARKERS` / `CLAIM_SUCCESS_MARKERS` —— 页面文案
  2. `REDEEM_PATTERN` —— 签到入口路径
  3. `BALANCE_AREA_PATTERN` —— 余额区 class
  4. `STREAK_PATTERN` / `REWARD_PATTERNS` —— 连续天数与奖励文案

  这些常量都集中在 `v2ex/main.py` 顶部，改文案不需要动逻辑。
- **改完必须同步**: 升 `VERSION`/`BUILD` → 跑 `python -m py_compile v2ex\main.py`
  → `git push origin master` → 让青龙重新拉取。四步缺一不可。
- **别再加「从 `/balance` 判断签到结果」的逻辑**。`/balance` 记录的是历史，
  这正是 v1.x 谎报成功的根源。它现在只作为余额解析失败时的兜底，且不参与成功判定。
